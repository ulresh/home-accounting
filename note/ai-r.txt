## Коротко

1. **Инкрементно из сети — частично да.** Есть API `Json.decodeFromStream(InputStream)`, который читает поток **порциями по мере поступления** (не загружая всё в память). Но модель — **блокирующая «pull»**: библиотека сама *вытягивает* байты из `InputStream`, а вы **не можете «толкать» (push) в неё свои буферы** по мере прихода из сокета. Асинхронного/неблокирующего (suspend, NIO, корутины) streaming-входа нет.
2. **Конец JSON-конструкции — да, находит сама.** Парсер определяет границу значения по синтаксису (баланс `{}`/`[]`, закрытие строк), внешний `Content-Length` или разделитель не нужен.

## Подробнее по п.1 — инкрементность

Что есть (JVM, помечено `@ExperimentalSerializationApi`):

```kotlin
// читает из InputStream порциями, низкий расход памяти,
// возвращает результат только когда значение полностью разобрано
val obj = Json.decodeFromStream<MyType>(inputStream)
```

Важные ограничения:

- **Pull, а не push.** Вы передаёте `InputStream` (например, `socket.getInputStream()`), и библиотека сама блокирующе читает из него столько, сколько нужно. Скормить ей вручную «вот пришёл очередной `ByteArray` из сети» — нельзя. Если у вас неблокирующий источник (Netty/NIO/ktor `ByteReadChannel`), его нужно обернуть в блокирующий `InputStream`-адаптер.
- **Нет частичного результата.** Пока верхнее значение не дочитано до конца, объекта вы не получите. SAX-подобного «событие на каждый токен по мере прихода» **публичного API нет** — внутренний лексер/ридер не выставлен наружу (в отличие от Jackson `JsonParser` или Gson `JsonReader`).
- **Память** при этом расходуется экономно: `decodeFromStream` декодирует напрямую в объект, не строя полное дерево `JsonElement`, и читает поток сегментами, отбрасывая разобранное. То есть «инкрементно по буферам» в смысле чтения — да; «инкрементно по выдаче результата» — нет.

## Подробнее по п.2 — поиск конца конструкции

Да, это встроено. Парсер дочитывает поток ровно до конца синтаксически завершённого значения и останавливается. На этом построен второй API — разбор **нескольких** JSON-значений из одного потока:

```kotlin
// лениво отдаёт по одному значению, сам определяя границы между ними
val seq: Sequence<MyType> = Json.decodeToSequence<MyType>(inputStream)
for (item in seq) { /* ... */ }
```

Режимы определения границ (`DecodeSequenceMode`):
- `WHITESPACE_SEPARATED` — значения подряд через пробелы/переводы строк (NDJSON / JSON-lines: `{...}\n{...}\n{...}`);
- `ARRAY_WRAPPED` — элементы внутри одного большого `[ ... ]`, отдаются по одному, не держа весь массив в памяти;
- `AUTO_DETECT` (по умолчанию) — определяет сам по первому непустому символу.

Здесь как раз видно, что библиотека **сама находит конец каждой конструкции** — иначе она не смогла бы делить поток на отдельные значения.

## Практический вывод

- Нужно «отдать сокет и пусть само вытянет один JSON и поймёт, где он кончился» → **`decodeFromStream` / `decodeToSequence` подходят** (это, например, и делает Ktor-клиент с kotlinx.serialization).
- Нужен **неблокирующий push-парсинг с backpressure** (кормить partial-буферами, получать токены/частичные результаты) → **только kotlinx.serialization не хватит**; берите Jackson (`JsonParser`, `non-blocking` async-парсер `JsonFactory` + `ByteBufferFeeder`) или комбинируйте kotlinx.serialization с обёрткой блокирующего потока поверх вашего async-канала.

Если уточните, какой у вас источник (raw-сокет, Ktor `ByteReadChannel`, Netty) — подскажу конкретную обвязку под `decodeFromStream`.

Да, это возможно — ключ в том, чтобы читать следующее значение в **`JsonElement`** (универсальный тип-«сырьё»), а потом по факту разобрать, что пришло.

## Базовый приём: декодировать в `JsonElement`

`JsonElement` — это абстрактный надтип, в который парсер уложит **любое** следующее значение: объект, массив, примитив или `null`. Тип определяется уже после чтения через `when`:

```kotlin
@OptIn(ExperimentalSerializationApi::class)
fun readNext(stream: InputStream) {
    val json = Json

    val el = json.decodeFromStream<JsonElement>(stream)   // читает ОДНО следующее значение, тип любой
    when (el) {
        is JsonObject -> {
            val user = json.decodeFromJsonElement<User>(el)        // дальше — в нужный класс
        }
        is JsonArray  -> {
            val users = json.decodeFromJsonElement<List<User>>(el)
        }
        is JsonPrimitive -> { /* строка/число/булево */ }
        JsonNull -> { /* null */ }
    }
}
```

Парсер сам находит конец значения (как обсуждали), поэтому ему не нужно заранее знать, объект там или массив — он смотрит на первый значащий символ (`{` или `[`) и читает до закрывающего.

## Поток из нескольких значений разного типа

Для последовательности смешанных значений — `decodeToSequence<JsonElement>`. **Важно явно указать `WHITESPACE_SEPARATED`**, а не оставлять `AUTO_DETECT`:

```kotlin
val seq = json.decodeToSequence<JsonElement>(stream, DecodeSequenceMode.WHITESPACE_SEPARATED)
for (el in seq) when (el) {
    is JsonObject -> { /* ... */ }
    is JsonArray  -> { /* ... */ }
    else -> { /* ... */ }
}
```

Почему не `AUTO_DETECT`: он решает по самому первому символу всего потока. Если первым придёт `[`, он сочтёт **весь поток одним массивом** (`ARRAY_WRAPPED`) и начнёт отдавать его элементы, а не «верхнеуровневые значения». Для потока вида `{...} [...] {...}` это сломает разбор. `WHITESPACE_SEPARATED` трактует каждое верхнеуровневое значение (и `{}`, и `[]`) как отдельный элемент.

## О чём помнить (компромисс)

- **`JsonElement` материализует значение целиком в дерево в памяти.** То есть для конкретного значения вы теряете «потоковость внутри него»: огромный массив будет полностью собран в `JsonArray`, прежде чем вы его получите. Чтение из сети остаётся инкрементным *между* значениями, но одно значение читается целиком.
- **Полиморфизм через дискриминатор тут не подходит.** Стандартный механизм sealed-классов с `"type": "..."` требует, чтобы значение было JSON-**объектом**, несущим поле-дискриминатор. Голый массив такого поля содержать не может, поэтому «объект ИЛИ массив» решается именно через `JsonElement`, а не через `@Serializable`-полиморфизм.
- Если значение — объект и тип внутри различается по полю, можно скомбинировать: сначала `JsonElement`/`JsonObject`, заглянуть в нужное поле (`el.jsonObject["type"]`), затем `decodeFromJsonElement<КонкретныйТип>(el)`.

## Чего библиотека НЕ даёт

Если нужно понять тип, **не материализуя значение** (например, заглянуть в первый токен гигантского массива и решать на лету) — публичного pull/token-API у kotlinx.serialization нет. Для такого сценария нужен Jackson (`JsonParser.nextToken()` / `currentToken()`), где можно посмотреть `START_OBJECT` vs `START_ARRAY` до полного чтения.

Если опишете формат потока (мешанина верхнеуровневых значений, NDJSON, или один тип с вариативной структурой) — подскажу точную комбинацию `decodeToSequence` + режим.

Безымянный (анонимный) `namespace { ... }` — это способ дать символам **внутреннюю связанность** (internal linkage), то есть ограничить их видимость **только текущей единицей трансляции** (одним `.cpp`-файлом). Это современная замена старому C-шному `static` на уровне файла.

В `SyncService.cpp` их три блока (строки 56–227, 277–340, 375–438), и лежат в них именно локальные вспомогательные вещи:

```cpp
namespace {
std::string randomCode(int n) { ... }        // генерация кода пэйринга
std::string localIPv4() { ... }              // определение своего IP

```

## Зачем это нужно

**1. Инкапсуляция — деталь реализации не «протекает» наружу.**
`randomCode`, `localIPv4`, асинхронные корутины-помощники (`aReadToSink` и т.п.) нужны только внутри `SyncService.cpp`. Их не должно быть видно в других файлах — снаружи существует только публичный интерфейс из `SyncService.h`. Анонимный namespace это гарантирует на уровне линковщика.

**2. Нет коллизий имён при линковке (ODR).**
Имя вроде `configureContext` или `randomCode` — очень «ходовое». Если бы оно имело внешнюю связанность и в другом `.cpp` (например, в другом сетевом модуле) появилась функция с такой же сигнатурой, линковщик выдал бы ошибку «multiple definition» или, хуже, молча слинковал бы не ту. Внутренняя связанность делает каждую копию приватной для своего файла.

**3. Возможность для оптимизаций.**
Компилятор знает, что символ никто извне не вызовет, поэтому легче инлайнит, выкидывает неиспользуемое, не обязан генерировать внешне видимый символ.

## Чем отличается от `static` и от именованного `namespace`

- `static std::string randomCode()` даёт тот же эффект внутренней связанности для **функций/переменных**, но анонимный namespace работает и для **типов** (можно объявить локальный `struct`/`class`), чего `static` не умеет. Поэтому в C++ он предпочтителен.
- Именованные `namespace asio = ...`, `namespace json = ...` (строки 28–31) — это **алиасы**, совсем другая задача (сокращение длинных имён). А `namespace ha { ... }` (строка 35) — это доменный namespace проекта, символы в нём **видны наружу**. Анонимный `namespace {}` вложен внутрь `ha` и, наоборот, всё в нём прячет.

Коротко: **именованные namespace группируют и раскрывают API, анонимный — прячет приватные помощники файла и защищает от конфликтов имён при линковке.**

Разница только в поведении при отсутствующем ключе — дереференс `cur->…` против `(*cur)[…]` тут ни при чём, это одно и то же обращение по указателю.

**`at(sn)`** — проверяемый доступ. Если ключа нет, бросает `std::out_of_range` с сообщением `map::at`. Никогда ничего не вставляет. Есть const-перегрузка, поэтому применим к `const map`.

**`operator[](sn)`** — вставляющий доступ. Если ключа нет, создаёт элемент со значением по умолчанию (для `std::string` — пустая строка) и возвращает ссылку на него. Только неконстантный; требует, чтобы тип значения был default-constructible.

То есть `m.at(k) = v` — «присвоить существующему», а `m[k] = v` — «создать при необходимости и присвоить».

В `CatalogLoader::add` нужен второй вариант. Механизм такой. Защита от повторной вставки события в приёме — по памяти, а не по файлу:

Три устройства:

1. A создаёт событие E (июнь). Файл A: `[E]`.
2. A ↔ C. У C файл: `[E]`.
3. C удаляет E. Файл C: `[E, D]`.
4. B ↔ C — первая синхронизация, C отдаёт файл целиком. Файл B: `[E, D]`. При приёме D событие E удаляется из `events_` у B.
5. B ↔ A — тоже первая, у A нет offset-а по B, поэтому A отдаёт свой июньский файл целиком, то есть E. У B в памяти E больше нет: `eq_edit` не срабатывает, соседний `eq_data` тоже (сравнивать не с чем). E вставляется в память и **дописывается в файл**.

Файл B: `[E, D, E]`. Одним проходом вперёд с применением удалений «на лету» второе E пережило бы загрузку — воскрешение. Сбор удалений по всему месячному файлу и отсев в `commit()` даёт правильный результат независимо от порядка.

## `RecRefDel` (`Types.h`)

```cpp
struct RecRefDel : RecRef {
    bool operator < (const RecRefDel &rhs) const {
	return event_datetime < rhs.event_datetime ||
	    (event_datetime == rhs.event_datetime && RecRef::operator<(rhs));
    }
    bool operator == (const RecRefDel &rhs) const {
	return event_datetime == rhs.event_datetime && RecRef::operator==(rhs);
    }
    std::string event_datetime;
};
```

`event_datetime` первым, хвост — делегированием в `RecRef`, чтобы порядок оставшихся трёх полей был ровно тот же и не разъехался при будущих правках.

Побочный эффект, о котором стоит знать: `MonthDeletions::Op::operator<` сравнивает `del` и `upd` (оба `RecRefDel`), поэтому порядок в `ops` поменялся — старшим ключом стал `event_datetime` удаляемой записи. Это и есть то, что делает поиск возможным.

## `MonthDeletions::CompareOps` (`Store.h`)

Прозрачный компаратор по образцу `CompareEventsSet`, `ops` теперь `std::set<Op, CompareOps>`:

```cpp
struct CompareOps {
    using is_transparent = void;
    bool operator()(const Op &a, const Op &b) const { return a < b; }
    bool operator()(const Op &a, const RecRefDel *b) const { return a.del < *b; }
    bool operator()(const RecRefDel *a, const Op &b) const { return *a < b.del; }
    bool operator()(const Op &a, const char *b) const {
	return compareDatetimeChar(a.del.event_datetime, b);
    }
    bool operator()(const char *a, const Op &b) const {
	return compareCharDatetime(a, b.del.event_datetime);
    }
};
```

Ключ-указатель — чтобы вызов читался так же, как уже существующий `store.events_.find(&op.del)`.

Сравнение с префиксом «ГГГГ-ММ» вынес в свободные `compareDatetimeChar`/`compareCharDatetime`, работающие со строкой; `compareEventChar`/`compareCharEvent` теперь делегируют в них. Логика та же побайтово, просто перестала быть привязанной к `shared_ptr<Event>` — иначе пришлось бы копировать в `CompareOps` эту неочевидную возню с длиной меньше 7.

Неоднозначности между перегрузками `const RecRefDel*` и `const char*` нет: `RecRefDel*` в `const char*` неявно не приводится.

## Одна причина, шесть падений

```cpp
void applyDeleteFromLoad(Store::TempEvents monthEvents, const RecRef &r)
```

Вектор снова принимается **по значению** — удаление применяется к копии и пропадает. При загрузке удаления не применяются вообще. Отсюда:

- `удалённое не видно после перезагрузки` (секция 1)
- `старая версия после правки не видна` (секция 1)
- `после перезагрузки ровно одна версия` (секция 1б)
- `удаление по чужому reference применилось` (секция 2)
- `после перезагрузки B Книга не воскресает` (секция 5)
- `удаление видно после перезагрузки` (`guitest`)

Сама запись удаления при этом формируется и кладётся правильно — «запись удаления лежит в файле удаляемого события» и вся секция 1б по расположению файлов зелёные. Ломается только применение при чтении. Лечится символом `&` в сигнатуре.

Не трогал: вы могли снять это намеренно, если планируете применять удаления при загрузке через `MonthDeletions`, а не на лету.

## Новая потеря данных от `mdels.ops.contains(*ep)`

`CompareOps` сравнивает только `event_datetime`, поэтому проверка означает «есть ли в месячном файле **хоть какое-нибудь** удаление за эту дату события», а не «удалена ли именно эта запись». Событие с чужой идентичностью, но той же датой, молча выбрасывается.

Добавил секцию 5б, которая это воспроизводит через обычный сценарий синхронизации:

```
A: addEvent("2026-06-11","Чай") → sync → у B есть «Чай»          [ ok ]
A: deleteEvent("Чай")           → sync → у B «Чая» нет            [ ok ]
A: addEvent("2026-06-11","Кефир") → sync
   → у B «Кефира» нет                                             [FAIL]
   → и в файлах B его нет после перезагрузки                      [FAIL]
```

Запись не задерживается, а теряется навсегда: offset у партнёра сдвинулся, повторно её не пришлют. Чтобы получить «удалена ли именно эта запись», нужен проход по `ops.equal_range(*ep)` со сверкой `edit_datetime`/`rec_no`/`dev_no`.
