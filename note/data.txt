getFilesDir()/Основная/device.jsonl
планирую 2 телефона Android и 2 ноутбука Ubuntu
собственный сомоподписной сертификат на каждом
идентификация по полному публичному ключу
[DN,"<публичный ключ>","<имя устройства>",NN]
[DN,"<публичный ключ>","<имя устройства>",NN,"disabled"]
Также каждому устройству присвоен порядковый номер.
Обратить внимание что чисто теоретически порядковые номера
устройств на каждом устройстве свои.
Иметь в виду при синхронизации.

Третий элемент - имя устройства, его задаёт владелец этого устройства
(при первом запуске приложения и потом в списке устройств).
Имя может отсутствовать или быть пустым.
Четвёртый элемент - количество изменений имени устройства.
При создании размести там 0, далее при каждом изменении увеличивай на 1.
Дальше идут необязательные строковые признаки, сейчас он один:
"disabled" - с этим устройством запрещена ПРЯМАЯ синхронизация.
Больше признак не значит ничего: записи такого устройства, пришедшие
через третье, принимаются как обычно.
Если признаки есть, имя обязано стоять на своём месте (пусть пустое).

Своё устройство отключить нельзя (сам с собой не синхронизируешься).
Имя своего устройства может менять только
пользователь: синхронизация его не меняет никогда.
Признак "disabled" для своего устройства не меняет ни пользователи
ни синхронизация.
Имена и признаки
ОСТАЛЬНЫХ устройств синхронизация переносит от собеседника.
При синхронизации своё имя не меняем никогда, имя собеседника всегда
принимаем то, что он передал, для остальных принимаем имя с большим NN.
Признак "disabled", поднятый для НАС в присланном списке, - ошибка:
отключивший нас не стал бы ничего передавать.

События

getFilesDir()/Основная/2020/2606.jsonl
{"header":["event_datetime","subject","cost","edit_datetime","rec_no","dev_no","people","volume","comment"],"reference":["edit_datetime","rec_no","dev_no","event_datetime"]}
["2026-06-12 10:00","Черешня",1200,"2026-06-12 10:09:12",0,1,{"volume":"2 кг"}]
["2026-06-12 10:00","Помидоры",300,"2026-06-12 10:09:12",1,1,null,"1.3 кг"}]
["2026-06-05","Джинсы",3760,"2026-06-12 10:09:20",0,1,"Мария"]
["2026-06-06","Стол",8200,"2026-06-12 10:09:21",0,1]
{"delete":["<edit-datetime-for-deleted-event>",RN,DN,"<event-datetime-for-deleted-event>"],"this":["<delete-datetime>",RN,DN]}
{"delete":["<edit-datetime-for-old-event>",RN,DN,"<event-datetime-for-old-event>"],"this":["<update-datetime>",RN,DN],"update":["<edit-datetime-for-new-event>",RN,DN,"<event-datetime-for-new-event>"]}.

Порядок и состав из reference использовать в разборе
{"delete":[...],"this":[...],...} (как в части delete, так и в
частях this и update).

последние null в строке не записывать.

cost можно с копейками, но чаще без.

При смене версии приложения header может быть записан новый.

Записи группируем в файл по значению "<event_datetime>".
В одном файле записи за месяц.
Месячные файлы складываем в отдельные папки на каждые 10 лет.

RN - добавочный номер для случая, когда несколько записей добавлены
на одному стройстве в одну секунду, обычно RN=0.

event_datetime в delete добавлен для поиска при синхронизации,
а в update для информации, если новое значение в другом файле.

Файлы событий не удаляем, не перезаписываем и не исправляем.
Только дозапись в конец файла.


Синхронизация.
По команде пользователя из интерфейса.
По возможности сохранить порядковые номера новых устройств при передаче.
Результат - передано N записей, принято K записей.
И в ходе синхронизации, и в результате показывать имя устройства
собеседника (пока оно неизвестно - так и писать).
На самом деле нам не сильно критично видеть именно точное количество
переданных/принятых записей, важно видеть именно сам факт передачи/приёма,
поэтому код в целях оптимизации может в ряде случаев считать не записи,
а блоки или какие-то другие объекты синхронизации.
Устройства в одной локальной сети.
JSONL over TLS.
Случайный свободный порт.
Desktop - телефон, телефон - телефон, - IP, порт,
код подключения (случайная буквочисленная последовательность длиной 8)
передаются через QR+камера телефона.
Desktop - Desktop скопировать или ввести вручную.
Для нового устройства запросить подтверждение, известные устройства
синхронизировать сразу.
Сопряжение начинает клиент строкой
[<код подключения>,"<имя базы>"]
или, если у него ещё нет данных,
[<код подключения>,"<имя базы>","empty","<имя своего устройства>"]
Сервер без данных отвечает ["empty","<имя своего устройства>"].
Имя своего устройства передаётся тут потому, что пустой стороне нечего
отдавать, а собеседнику имя знать надо. В остальных случаях имя доезжает
в самом файле устройств: смена имени меняет его sha1, значит файл будет
передан при ближайшей синхронизации.
Про NN собеседник узнаёт из файла устройств, из hello приходит только имя.

С устройством, помеченным "disabled", прямая синхронизация не проводится:
клиент к нему не подключается, сервер после верного кода отвечает
["error","disabled"].
При синхронизации проверять совпадение имени текущей базы данных,
при несовпадении предлагать переключиться или создать новую и переключиться.

При первом сопряжении устройства без данных у него можно менять
собственный DN (и даже нужно, поскольку при старте у всех устройств
собственные DN одинаковые, что при первой синхронизации следует поменять,
только не оба, а одного).
При синхронизации надо делать map с пространства DN второго устройства
на пространство DN текущего устройства.

При синхронизации отдавать файлы (добавленный с прошлой синхронизации
хвост), а не память.

Хвосты файлов отдавать без разбора, для защиты от испорченных файлов
передавать их в конструкциях вида
["event-tail",202606,size]\n<содержимое файла>\n
["device",size]\n<содержимое файла>\n
["people",size]\n<содержимое файла>\n
["catalog",size]\n<содержимое файла>\n

При вливании игнорировать события с DN after map == this DN.
Также игнорировать события, у которых DN не найден в map.

При синхронизации не вставлять повтор {"delete":[...],...} если он уже есть.
Между синхронизациями {"delete":[...],...} не хранить.
Подгружать их отдельным проходом.

Будь готов к тому, что от собеседника при синхронизации придёт
другой порядок/состав полей в {"header":[...],"reference":[...]}.
А поскольку мы его запишем как получили (только сделаем DN map),
то и у нас в одном файле появятся строки с разным порядком/составом полей.
Если у собеседника более новая версия с расширенным составом полей,
то обрезав мы осложним собственный будущий переход на новую версию,
а кроме того ещё и распространим обрезанные данные.

Заголовок в строках файлов событий хранится не свой, а собеседника.
В начале пишу canonicalHeader, причём как раз свой (нужен для случая
запуска новой версии со старой базой), для месячных файлов пишу заголовок,
если последний полученный от собеседника заголовок отличается от
моего канонического.


Первый запуск приложения: спросить имя этого устройства и имя базы
данных. Имя базы должно совпадать у синхронизируемых устройств.

Ввод. Новые значения сразу записывать в соотвествующий файл.
Не делать отдельной команды Сохранить.
Таблица. При запуске приложения читать все файлы в память.
В таблице фильтры по названию и по каталогу.
Поиск.
Удаление. Исправление (записывается как удаление и новое событие).
"edit_datetime" не отображается.
